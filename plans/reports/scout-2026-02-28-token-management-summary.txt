================================================================================
TOKEN MANAGEMENT ARCHITECTURE
================================================================================

INPUT TOKENS (from config):
  ├─ bearerToken           [REQUIRED] Google Labs API access token (3h+ expiry)
  └─ sessionToken          [OPTIONAL] __Secure-next-auth.session-token (ST→AT refresh)

KEY MECHANISM: ST→AT (Session Token → Access Token)
  └─ Endpoint: https://labs.google/fx/api/auth/session
  └─ Method: GET with Cookie header

REFRESH STRATEGY:
  ├─ Proactive: Refresh when < 1 hour remaining
  ├─ Reactive: Refresh on 401 + retry
  └─ Deduplication: Prevents concurrent refresh requests

API FLOW:
  Client.generateImage() 
    → withTokenRefresh()
      → ensureValid() [checks if refresh needed]
        → doRefresh() [calls ST→AT endpoint if needed]
      → execute API call
      → on 401: forceRefresh() + retry once

================================================================================
AUTHENTICATION HEADERS
================================================================================

DEFAULT HEADERS (all requests):
  Content-Type: application/json
  Origin: https://labs.google
  Referer: https://labs.google/
  Authorization: Bearer <bearerToken>

FOR SESSION REFRESH (ST→AT):
  Cookie: __Secure-next-auth.session-token=<sessionToken>

================================================================================
ERROR CODES (AUTH-RELATED)
================================================================================

401 Unauthorized
  → Triggers: forceRefresh() + retry once (if sessionToken configured)

403 Forbidden
  → With "RECAPTCHA": needs reCAPTCHA token
  → With "PERMISSION_DENIED": auth issue

"Cannot refresh token: no sessionToken configured"
  → Session token required for auto-refresh

"Session refresh failed: {status} {statusText}"
  → Network error on ST→AT endpoint

"Session cookie expired or invalid"
  → Response contains error field (e.g., "ACCESS_TOKEN_REFRESH_NEEDED")

Add to TokenManager:

Expose via Client:

    accessToken: string;
    expiresAt?: Date;
    user?: { email: string; name: string };
  }>

Benefits:
  ✓ Reuses existing ST→AT logic
  ✓ Returns token + metadata
  ✓ Doesn't update client state
  ✓ Handles errors consistently
